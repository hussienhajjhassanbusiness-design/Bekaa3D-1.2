# ADR-028: Keyed, monthly-rotated IP hashes - a database salt plus an environment pepper, old salts deleted

**Status:** Accepted
**Date:** 2026-10-16
**Source basis:** Owner decisions of 2026-10-16 on the VS-046 plan (Q1 to Q12, amendments A to G); SRS SEC-25, SEC-26, §23; [ADR-018](ADR-018-authentication-epoch.md); [ADR-024](ADR-024-cash-on-delivery-and-courier-priced-shipping.md); plan [`VS-046-security-retention-plan.md`](../plans/VS-046-security-retention-plan.md)

## Context

SEC-25 asks for "salted, rotating IP hashes". Until VS-046, `hash_ip` was `sha256(IP_HASH_SALT:ip)` with one static salt from the environment. It was never rotated, so every hash ever written stayed linkable. Anyone holding that salt could also reverse the hashes: the IPv4 space is only about 4·10⁹ guesses.

The plan verified that **no code compares an `ip_hash`** across rows or across time. The column is written to `sessions` and `audit_logs`, read back only by mappers, and omitted from the audit API. Rate limits and the login throttle key on the raw IP instead. So rotation breaks no behaviour. Losing the ability to link old hashes to new ones is the point.

## Decision

1. **Keyed hash.** `hash_ip(ip) = HMAC-SHA256(K, ip)`, with `K = HMAC-SHA256(pepper, "bekaa3d/ip-hash/v2:" || salt)`. The output is still 64 lowercase hex characters.
2. **Two secrets, stored in different places.**
   - The **pepper** is the environment variable `IP_HASH_SALT`. The name is kept so no `.env` or CI step breaks. It is a `SecretStr`, so it prints as `**********`.
   - The **salt** is 32 random bytes in `ip_hash_salts`. It is generated by `gen_random_bytes(32)` inside PostgreSQL, so it never travels as a bound parameter.
   - A database dump alone cannot reverse a hash, and neither can the environment alone.
3. **Exactly one salt, and old ones are deleted.** A partial unique index allows at most one current row. Rotation deletes every row and inserts a fresh one in one transaction, so the grace window in the database is 0. Keeping old salts would let anyone holding them and the pepper link every month.
4. **Rotation once per UTC calendar month.** `rotate_ip_salt` runs daily at 00:23 and at every worker start. It rotates when the current salt predates the current UTC month.
   - arq skips ticks missed while the worker was down, so a `day=1` cron alone would lose the month.
   - A transaction-scoped advisory lock and a re-check under that lock make concurrent and repeated runs no-ops.
   - Each rotation writes one `ip_hash_salt.rotated` audit row, with ids only.
5. **Synchronous `hash_ip`, served from an in-process key.**
   - The API loads the key at startup. `IpHashKeyRefreshMiddleware` reloads it when it is older than 60 s, or when none is loaded.
   - Reloads are throttled to one attempt a minute by a timestamp guard that is not bound to any event loop.
   - A failed reload keeps the old key. With no key at all, `hash_ip` returns None and the row stores `ip_hash = NULL`: closed for privacy, open for availability.
6. **`PHONE_HASH_SALT` is unaffected.** ADR-024's phone hash must match across orders, so it is never rotated.

## Consequences

- **Staleness.** After a rotation commits, each API process keeps the old derived key for up to 60 s, plus its next request. Hashes written in that window can still be linked to the previous month's hashes. This is accepted: about a minute a month, and no code compares hashes.
- **Changing the pepper needs a restart.** `get_settings()` is `lru_cache`d, so a new `IP_HASH_SALT` is read only by a new process. Every process should restart together, or hashes from a mix of keys are written for a while; nothing breaks either way.
- **Backups.** A database backup contains the salt that was current when it was taken. Unlinkability for a past month therefore holds only once every backup holding that month's salt has expired. VS-047 states the backup retention.
- **Legacy hashes** written with the static salt stay as written. No production or staging data existed at this change, so there was no backfill.
- **Monitoring.** A failed rotation raises a class-only `IpHashSaltRotationError`, so arq marks the job failed. Logs, audit rows and errors carry ids and error classes, never salt bytes or the pepper.

## Alternatives considered

- **Database salt only.** The salt would sit beside the hashes in the same dump, which is exactly the leak SEC-25 guards against.
- **Rotating the environment salt by redeploy.** That is a monthly manual secret change, not a job.
- **`async hash_ip` reading the salt per request.** That would mean 16 call sites, one extra query on every hashing request, and a fake session in every unit test, all to remove a 60 s staleness that harms nothing.
- **Versioned salt history with a grace window.** Nothing ever reads an old salt, and keeping them defeats the rotation.
